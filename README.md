# GT Matter Packer

面向 GTNH 2.8.4 的独立附属 Mod，版本 **0.3.1 alpha**。依赖实例现有的 Matter Manipulator **0.0.51-GTNH**、Forge Multipart **1.7.2**、CodeChickenCore **1.4.10** 和 UniMixins，不替换原 Mod。

新物品直接继承原版 MK-III，沿用其充电、升级、菜单、选区、建造、复制、移动和外观。新增打包／部署操作保存真实机器数据，并消耗该份数据部署一次。携带包裹时禁用原版持续建造操作，以防误操作。

## 使用

1. 将 `build/libs/gtmatterpacker-0.3.1.jar` 放入**测试实例**的 mods。升级时移除旧版 GT Matter Packer jar，仅保留一个版本。多人游戏需要服务器与客户端都安装；保留原物质操纵者 Mod。
2. 用原版物质操纵者 III + 末影之眼无序合成新物品。该合成保留原工具 NBT，包括电量、设置和升级。这只是首版测试配方。
3. 手持新物品，对空中右键打开原圆环，进入“选择模式 → 打包储存”。原来的五种模式仍然在同一个模式圆环中。
4. 再打开圆环，选择“标记打包区域”，依次右键确认区域两角。停止机器后，从圆环选择“执行打包”，或按原习惯对空中按住 Shift＋右键约半秒。成功后原区域被取走。
5. 前往同一存档任意维度，打开圆环选择“标记部署位置”，右键确认位置。该位置是区域最小 X/Y/Z 角；通常点方块表面取相邻格，潜行时点方块取该格。
6. 再打开圆环选择“执行部署”，或对空中按住 Shift＋右键约半秒。部署采用已经标记的位置，不使用执行时的准星位置。保留原方向，不旋转。

全部操作通过圆环和原物品交互完成，没有命令入口和独立快捷键。新模式自动根据是否携带包裹显示打包或部署操作；操作失败提示仍显示在聊天栏。选择原有任一模式会退出打包储存模式。

每次操作每个实际方块消耗 512 EU，创造模式免费。使用者必须是打包记录的所有者。没有自动从 AE 提取材料的步骤，部署使用打包时取走的实际机器。

## 多方块与自定义构造

0.3.1 修复采矿场 GT 裸框架被误报“方块实体缺失”：框架只有带覆盖板等额外状态时才需要实体，因此允许无实体的 GT 框架，同时保留带实体框架的数据校验。真实机器或仓室缺失实体仍会被拒绝，并在提示中包含方块名称、元数据和位置。部署元数据校验支持 GTNH 的 16 位范围，不再错误限制为原版的 0–15；例如框架材料元数据 316 会按原值恢复。

0.3.0 将整组选区作为一个整体恢复，支持框选完整 GT 多方块、多个机器组合、带孔外壳、管线阵列或尚未成型的自定义构造。操作仍全部在原来的“打包储存”圆环模式中完成，无需额外模式或命令。

取走时先断开整组方块实体，再逆序移除结构方块。部署时先放齐支撑与结构方块，再恢复所有方块实体数据，最后重连网络、通知邻居。GT 多方块控制器在正常游戏刻初始化后重新检查结构、收集仓室；这包括 MTEMultiBlockBase 的派生机器。程序提示安排的控制器检查数量，不把“已经放下”当作“已经成型”。

请将控制器、全部结构方块、仓室、线圈及需要随迁的管线都框入选区。它不会自动沿结构追踪边界，也不会判断框选是否截断机器；原来未完成的结构仍可打包，部署后可能仍不成型。结构外的电源、网络和绑定设备需要重新接入。

## 支持范围与限制

- 同存档跨维度；退出、重进后记录仍存在。源维度无需在部署时加载。
- 每个物品同时携带一份记录，选区体积最多 **32,768 格**（按整个包围盒计算，含空气格），区域内每格距玩家不得超过 256 格。操作仍同步执行，大选区可能造成明显卡顿；压缩数据仍受 16 MiB / 解压 64 MiB 限制。
- 支持普通方块、GT 与原版方块实体。GT 活跃机器拒绝打包；已停止机器的进度、待输出物、流体、库存等保存在完整 NBT 中，并对关键字段作往返检查。
- 新增通用方块实体和 Multipart 的 NBT 恢复路径。普通实体须通过完整 NBT 往返检查；GT 检查库存、流体、覆盖板、待输出、进度、储能与机器类型。AE 和 Multipart 仅忽略已确认的 AE 延迟写入网格节点字段，不能忽略物品或部件配置。不能完整恢复的实体会在取走前明确拒绝，并显示坐标和原因。
- GT 激光／数据管道在整组实体恢复后更新相邻网络；Multipart 恢复部件后调用移动回调并同步。AE 沿正常实体生命周期重建连接，并检查源网络 BUILD 权限。这些适配仍待整合包内逐类验收。
- 保留方块、元数据、方块实体 NBT，部署只改通用顶层坐标。外部绝对坐标、跨区块绑定和存在其他存储中的状态不能通过通用 NBT 保证随迁；需要具体 Mod 适配。通用检查通过也不能等同于该 Mod 的全部运行逻辑已验证。
- 不搬运实体，不旋转或镜像。整个目标长方体（包括原空气格）必须为空且已加载。
- 检查基础权限、GT 机器所有权、Forge 破坏与放置事件；不同领地插件仍需服务器验证。
- “任意构造”指选区内的静态方块组合及可恢复实体，不承诺所有 Mod 特殊机器、运动中活塞或存储在世界外部数据里的结构均能迁移。

## 存储与恢复

数据统一位于主世界存档的 `gtmatterpacker/packages/<UUID>.nbt`，物品只携带 UUID，不装入大体积机器 NBT。请备份**整个存档**，不能只备份区块或玩家文件。不同存档中同一个物品编号没有意义。

记录状态：`PACKING → PACKED → DEPLOYING → CONSUMED`。先持久化完整 NBT 与操作状态，再改世界；同步保存世界区块后才完成状态切换。复制物品不能再次部署已经消耗的编号。异常尝试回滚已触及的位置，记录仍保持锁定，避免自动重试造成复制。

圆环“包裹管理 → 查看记录”显示自己的未消耗记录。如果工具丢失，手持另一把空的新工具，进入打包储存模式，选择“包裹管理 → 找回最近包裹”，重新绑定自己最新的 `PACKED` 记录。多个包裹可按最新到最旧的顺序逐一找回、部署。原工具副本与新工具仍共用一次部署资格。

如果副本工具携带的编号已经由另一把工具成功部署，可通过“包裹管理 → 清除已部署编号”继续使用该工具。它不能清除未部署或锁定记录。

`PACKING` 或 `DEPLOYING` 在重启后保持锁定，需要管理员对照记录中的 Source/Target 坐标、维度及 Blocks 数据检查世界，再从完整备份恢复或人工修复。首版不提供自动解锁命令。文件原子替换和同步写入不能保证抵御所有磁盘、断电或外部存档回滚问题；不得将其视为已验证的生产级事务系统。

## 构建与验证

Windows：`gradlew.bat build`。使用 GTNH Gradle，Forge 1.7.10，依赖锁定到本次实例版本。构建及单元测试结果见 VALIDATION.md。游戏内验收步骤见 TESTING.md。

兼容补丁仅对新物品保留包裹编号、模式和尺寸字段，防止上游 `setState` 重写 NBT 时清除这些字段。原物质操纵者的保存逻辑保持原样。圆环扩展使用原菜单公开的选项列表，没有反射或替换原 Mod 文件。

原物质操纵者上游：https://github.com/GTNewHorizons/MatterManipulator/tree/0.0.51-GTNH ，源码提交 `517635dc62e2fea1c428779541e9d2683ba50951`。项目采用 LGPL-3.0-or-later，包含与上游对应的许可文本；新物品通过依赖原 Mod 复用纹理和行为，不复制其素材。
